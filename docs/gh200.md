# GH200 rental rehearsal

The local preparation produces a private transfer bundle with the committed source/history,
frozen tokenizer, verified 105M-token pilot pack, and a finite assistant rehearsal. It contains no
virtual environments, account credentials, model downloads, or local checkpoints. Do not publish
the corpus payload. The one-GPU workflow is separate from the 800-step scientific pilot.

Build from a clean checkout after checks and commits:

```bash
python -m scripts.gh200_check bundle --output /external/gh200-bundle \
  --data /mnt/speck-data/speck/data/flagship-pilot-105m \
  --tokenizer /mnt/speck-data/speck/tokenizer-final-mistral-v1 \
  --assistant /mnt/speck-data/speck/gh200-readiness-20260918/assistant-rehearsal-2
```

This writes `gh200-bundle.tar.gz` and a transfer receipt with its SHA-256. The bundle manifest pins
every copied file and the Git commit. Use the supplied SSH host, port, and user to copy the archive
and transfer receipt. No Vast API credentials are needed. Verify its SHA-256 after transfer, then
extract it into a private directory on the machine's persistent disk.

Reserve at least 200 GB of local disk; the runner requires 128 GiB free before starting. Confirm
the offer is an ARM64 GH200 with one allocated GPU and a working NVIDIA driver, and record the
instance ID, hourly rate, storage/network charges, and intended deletion time. The user controls
rental creation and deletion; stopping training does not delete the rented instance.

On the host, assuming the extracted directory is `/workspace/gh200-bundle`:

```bash
cd /workspace/gh200-bundle
git clone --branch codex/gh200-readiness code.bundle code
cd code
# Use uv 0.12.1 (the preparation version), installed for ARM64, and Python 3.10.
uv sync --locked --python 3.10 --extra gpu --extra linear --group dev --group transformers
uv run --no-sync python -m scripts.gh200_check bind /workspace/gh200-bundle
uv run --no-sync python -m scripts.gh200_check run /workspace/gh200-bundle \
  --output /workspace/gh200-results/attempt-1 --seconds 5400
```

Read the actual branch from `bundle.json` if rebuilding from another branch. The lock contains
ARM64 CUDA 12.8 PyTorch 2.9.1 and Triton 3.5.1 wheels; successful installation and execution still
need confirmation on the rented image. Do not copy this workstation's x86 virtual environments.
Use a persistent SSH terminal (`tmux`, if installed), retain the console log, and monitor the
instance during this first qualification. No compilation or W&B credentials are needed.

The command verifies the clean source commit and all input hashes, records runtime/GPU identities,
and runs these steps with a shared 90-minute execution deadline:

1. Reopen the pilot pack, scan 64 loader batches, and replay saved batches in a fresh process.
2. Check KDA numerical behavior, gradients, recurrence/cache, and timing at bounded lengths.
3. Train four full-size 4K base steps using real pilot data, restart from step two in a new process,
   and compare model/optimizer tensors plus exact loader/RNG state. The diagnostic batch is one
   sequence; this is not the pilot optimization schedule.
4. Exercise native cached generation and export/tokenizer/Transformers parity for that checkpoint.
5. Initialize SFT from the identified base, train the finite assistant rehearsal in four optimizer
   steps, repeat the same restart check, then check generation and export again.

Any failing phase stops the sequence. Logs, failed checkpoints, and a failed result remain available.
The total deadline covers supervised child execution, with cleanup grace; hashing/comparison and
installation/transfer also consume rental time. It is not a provider billing cap or an automatic
instance deletion mechanism. The result reports allocated GPU-hours for this attempt only; keep
earlier attempts, idle time, downloads, storage, and bandwidth in the rental cost record.

Download the complete result directory or, if time/storage is constrained, its JSON receipts,
worker logs, checkpoint metadata, exported parity reports, and any failed-phase artifacts before
deleting the instance. Full checkpoints are useful for local diagnosis; they are disposable
engineering models, not release candidates. Re-run a failed phase only after recording its cause.

One GH200 can qualify its ARM64 software stack and single-worker behavior. Four-worker collective
behavior, distributed restart, scheduler interruption/requeue, compilation, sustained pilot batch
throughput, and actual model quality remain checks for the later allocation. Follow the separate
[qualification](../experiments/qualification/README.md) and [Slurm](slurm.md) procedures there.
The prepared [assistant contract](assistant.md) and [capability graders](evaluation.md) remain
independent of the rental: code grading can run locally in its isolated environment.
